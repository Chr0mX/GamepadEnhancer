How it works

From your input and the network to a pad report

One engine thread reads a snapshot of your settings, the current mouse and keyboard state and whatever a Network API client (such as Axiom) has set, and sends one report to the virtual controller. Aiming, recoil and stick shaping are done by that client; this app is the pad host.

Architecture

The UI never talks to the driver. It edits a settings object; a separate engine thread owns the virtual controller and does all the timing. That keeps a slow redraw from ever delaying a report.

Core

ControllerEngine, EngineSettings, StickMath, MouseLook, RemoteControlState. No UI types, so the logic compiles and tests without Avalonia.

Input

Two capture back ends behind one IInputSink, and a manager that keeps exactly one of them active.

UI

Avalonia 11 with a custom dark theme. It writes settings; the engine reads a snapshot each tick, so no locks are held while talking to the driver.

The output pipeline

On every engine tick the report is built in the same order. A stage that is switched off simply passes its input along.

  1. Mouse lookOptional: mouse movement becomes a right-stick value (sensitivity, response curve, game dead zone, release time).
  2. Network commandsA client can set the left stick, right stick, triggers and buttons. A right stick it sets replaces the mouse-look value while it is set.
  3. BindingsKeys, mouse buttons and wheel notches mapped to buttons or triggers are applied, including turbo toggling.
  4. ReportConvert percent to the controller's axis range, then submit once. A report goes out only when it changed, plus a 250 ms heartbeat.
Why one report per tick

The ViGEm client can auto-submit on every axis write. The app turns that off and calls SubmitReport() once per tick, outside its internal lock, so a slow driver call never blocks the mouse and keyboard hooks.

The two axis ranges

The two virtual pads count differently, and getting that wrong was one of the bugs fixed along the way.

So a 25 percent downward stick is DS4 Y = 160 but needs a negative Y on Xbox. The engine flips the Y sign for Xbox so a direction always means the same thing on screen. Rounding is banker's rounding, matching the C# Math.Round.

The Network API drives the sticks

Turn on the Network API on the Network tab and another program on your network can drive this pad with MAKCU-style text commands over TCP: sticks, triggers and buttons, with an optional hold time. A token is required and the setting is off by default. Axiom uses this to apply its aim, recoil and stick behaviour, so none of that is built into this app any more.

The same connection also carries your mouse buttons back: a client sends km.mouse_stream(1) and the app pushes km.mouse(mask) lines, so the other program can use a button as a trigger without a second port or token. Everything a client set is released when it disconnects or goes silent.

The full command list is in docs/NETWORK_API.md in the repository.

Input capture

Low-level hooks

The classic WH_MOUSE_LL and WH_KEYBOARD_LL hooks. Simple and reliable, and the default. Windows gives hook callbacks a short time budget, so the callbacks only record state and return.

Raw Input

A hidden window registers for mouse and keyboard with RIDEV_INPUTSINK, so input arrives even when the game has focus. It tells real devices from software ones: hDevice == NULL marks a synthetic event, and the fake Shift Windows sends around Num Lock keys is ignored.

The InputStateManager runs exactly one method. On a switch it releases anything held, so a key that was down under the old method cannot stay stuck. If a device is removed or the chosen method fails to start, it falls back and says so. The choice is stored app-wide in settings.json, not in profiles.

Key bindings and turbo

Up to 17 bindings map a keyboard key or mouse button to a controller action: any face button, bumper, stick click, D-pad direction, Start or Back, a trigger, or the Guide / PS button. Each can have turbo, pressing and releasing at 1 to 30 Hz while the key is held. The app only presses controller buttons; it never types into your keyboard.

Profiles and the default

A profile is a plain JSON file in profiles/ beside the exe, so they are easy to copy, share or edit. Default.json ships inside the app as an embedded resource, is written to profiles/Default.json on first run, and is loaded at startup when it is valid. If the file is missing or broken the app falls back to the embedded copy.

The full list of fields is in the reference.
