How it works

From a mouse click to a stick value

One engine thread reads a snapshot of your settings and the current mouse and keyboard state, works out where the right stick should be, and sends one report to the virtual controller. Everything on this page is the same maths the app runs.

Architecture

The UI never talks to the driver. It edits a settings object; a separate engine thread owns the virtual controller and does all the timing. That keeps a slow redraw from ever delaying a report.

Core

ControllerEngine, EngineSettings, StickMath, LowPassFilter, RecoilPattern. No UI types, so the logic compiles and tests without Avalonia.

Input

Two capture back ends behind one IInputSink, and a manager that keeps exactly one of them active.

UI

Avalonia 11 with a custom dark theme. It writes settings; the engine reads a snapshot each tick, so no locks are held while talking to the driver.

The output pipeline

On every engine tick the stick position goes through the same stages in order. A stage that is switched off simply passes its input along.

  1. Base driftStart from the pull direction and drift percent. Down is (0, +d), Up (0, -d), Left (-d, 0), Right (+d, 0).
  2. Recoil stepWhile aim and fire are both active, the current pattern step replaces the drift with an absolute position.
  3. Center RadiusOptionally lift the point away from the center (Lift), or add a small circular or random wobble (Shake / Circle) so the stick is never dead-centered.
  4. FilteringIf the filter is gated on, add the micro-oscillation or the low-pass wiggle on the axis across your drift.
  5. BindingsKeys mapped to buttons, triggers or the left stick are applied, including turbo toggling.
  6. ReportConvert percent to the controller's axis range, then submit once. A report goes out only when it changed, plus a 250 ms heartbeat.
Why one report per tick

The ViGEm client can auto-submit on every axis write. The app turns that off and calls SubmitReport() once per tick, outside its internal lock, so a slow driver call never blocks the mouse and keyboard hooks.

So 25 percent drift Down is DS4 Y = 160 but the Xbox "pull down" needs a negative Y. The engine flips the Y sign for Xbox so a direction always means the same thing on screen. Rounding is banker's rounding, matching the C# Math.Round.

Recoil patterns

Recoil is aim, then fire. The aim key (Right, Left, Middle mouse, or off) is Hold or Toggle. The fire key plays the pattern only while aim is active. A Start Delay waits before the first step; Loop repeats the pattern while fire is held.

A pattern is text: steps separated by |, each step x:y:ms with x and y as absolute stick percent and ms as the time to hold it. The engine runs on a 10 ms tick, so step times are rounded to whole ticks (17.3 ms plays as about 20 ms). Pattern files in patterns/*.config use one x,y,ms line per step.

The preview is stick positions, not the view path

A game turns stick deflection into camera speed. Holding the stick to the right keeps the view turning; it does not park it at a point. A circle of stick positions therefore does not draw a circle on screen. It is the shape of the input, which is exactly what the preview shows.

Stick filtering

Filtering adds a tiny, very fast wiggle on the axis across your drift, so Left and Right wiggle on Y while Up and Down wiggle on X. It is gated by a button with Hold or Toggle, and it speeds the engine loop up while it runs (default 2 ms, choices 2, 4, 8 and 16).

RC-Style Micro-Oscillation

Every tick alternates the target between centre + N and centre - N axis counts. Near the ends of the range the swing shrinks so it never clips. On Xbox one DS4 count is scaled by 32767/127.

Exponential Low-Pass

A square wave of period 16 ms x N drives a filter with alpha = 1 - exp(-dt / tau), tau = 4 ms x N. The drive is scaled by 100/127/tanh(1) so the filtered peak is exactly N counts. Values within 0.001 percent snap to the target.

With filtering off and nothing changing, the app sends about 4 reports per second (the heartbeat). With a 2 ms filter loop it sends up to 500 per second, which is why the output path was made so cheap (see the performance case study).

Input capture

Low-level hooks

The classic WH_MOUSE_LL and WH_KEYBOARD_LL hooks. Simple and reliable, and the default. Windows gives hook callbacks a short time budget, so the callbacks only record state and return.

Raw Input

A hidden window registers for mouse and keyboard with RIDEV_INPUTSINK, so input arrives even when the game has focus. It tells real devices from software ones: hDevice == NULL marks a synthetic event, and the fake Shift Windows sends around Num Lock keys is ignored.

The InputStateManager runs exactly one method. On a switch it releases anything held, so a key that was down under the old method cannot stay stuck. If a device is removed or the chosen method fails to start, it falls back and says so. The choice is stored app-wide in settings.json, not in profiles.

If a button seems stuck (its up event was missed, for example after a focus change) the engine polls GetAsyncKeyState about every 30 ms and clears it after three agreeing polls.

Key bindings and turbo

Up to 16 bindings map a keyboard key or mouse button to a controller action: any face button, bumper, stick click, D-pad direction, Start or Back, a trigger, or a left-stick direction. Each can have turbo, pressing and releasing at 1 to 30 Hz while the key is held. The app only presses controller buttons; it never types into your keyboard.

Profiles and the default

A profile is a plain JSON file in profiles/ beside the exe, so they are easy to copy, share or edit. Default.json ships inside the app as an embedded resource, is written to profiles/Default.json on first run, and is loaded at startup when it is valid. If the file is missing or broken the app falls back to the embedded copy.
