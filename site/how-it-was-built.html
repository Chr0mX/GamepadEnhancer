How it was built

From one big form to a testable engine

The project started as a single WinForms window and grew through about twenty-five betas. This page covers the path, how each piece was checked, and what went wrong.

Timeline

  1. April 2026

    Version 1: WinForms

    One 1,886-line MainForm. A right-stick jitter to counter recoil, a base drift, key bindings and turbo. It worked, but the logic and the UI were tangled together.

  2. June 2026

    Recoil replaces jitter

    The jitter idea was reworked into recoil patterns: a list of stick positions played while you fire.

  3. August 2026

    Dark mode and flat UI

    Two pull requests gave the WinForms app a dark theme and a flat look, which also showed how hard the form was to scale.

  4. October 2026

    Beta 1.1: Avalonia

    The UI was rewritten in Avalonia 11 with proper scaling, a dedicated tab for PC to controller, and settings preserved. Negative filtering values were introduced: a fast, invisible wiggle of the reported value.

  5. October - November 2026

    Betas 1.2 to 2.2

    Aim then fire triggers, Hold or Toggle, Circle preset and Loop, two filter algorithms, a Filter rate, an Input capture dropdown with Raw Input, a lag fix, Down/Up/Left/Right pull directions and a shipped default profile. The table below lists the headline of each.

The stack

C# on .NET 8

One project, GamepadEnhancer, Windows only because of the hooks, Raw Input and the driver.

Avalonia 11.2.3

Cross-platform UI with real layout and scaling. Custom dark theme, a recoil preview control and dialogs.

Nefarius.ViGEm.Client

Version 1.21.256, the managed client for the ViGEmBus driver. AutoSubmitReport is off; the engine submits.

Win32 P/Invoke

Hooks, Raw Input, GetAsyncKeyState, thread priority and timer resolution.

JSON on disk

Profiles, patterns and settings.json sit next to the exe so everything stays portable.

GitHub Actions

One workflow builds on Windows and publishes a zip to a release.

Testing without a driver

Most of the work was done in a Linux sandbox where the Windows driver, the real input hooks and the NuGet feed were all unavailable. The answer was to keep the interesting logic free of those things and test it directly.

  • Pure logic first. Percent to axis, pull directions, lifting, the filter maths and pattern parsing live in plain classes with no UI or driver types.
  • A stub controller. The engine tests compile the real engine source against a small stub that records every axis and button write and every SubmitReport(). Tests then assert exact values, such as DS4 Y = 160 for 25 percent Down, or X 116 to 140 for RC -12.
  • Scratch projects. Separate throwaway projects covered the engine, the capture manager, performance and the circle preset, so the repository stays clean.
  • The UI is verified on Windows CI. The sandbox could not compile Avalonia, so each push was built by GitHub Actions on Windows; builds 78 to 94 all passed.
  • This website. The two labs above use a JavaScript port of the same maths. A Node test checks the same expected numbers as the C# tests (for example DS4 25 percent is 160, Xbox 25 percent is 8192).

Case study: the lag when filtering was on

The report: in game, the pad flipped between "controller" and "PC" very quickly, and the PC lagged, but only while filtering was enabled. The cause was the output path, not the maths.

Measurement (simulated 0.5 ms driver call)BeforeAfter
Filter loop CPUabout 102 percentabout 30 percent
Hook callback wait131 to 178 microseconds3 to 4 microseconds
Worst hook stall1.8 to 15 msunder 0.5 ms
Reports per second, static stick1004
  1. Submit only on changeA report is sent only if the stick or buttons differ from the last one, plus a 250 ms heartbeat. A static stick went from 100 to 4 reports per second.
  2. One submit per tick, outside the lockAuto-submit was disabled and SubmitReport() is called after the engine releases its lock, so the hook threads never wait behind a driver call.
  3. A leaner filter loopThe fast loop does only the filter work, with a user-chosen period (2, 4, 8 or 16 ms) so a slower rate can cut the load further.
What the code could not fix

Some games switch their on-screen prompts between controller and mouse the moment any input appears on either device. Fewer, steadier reports help, but this behaviour is the game's. Tips are in the FAQ.

Builds and releases

A single workflow, build.yml, is started by hand (workflow_dispatch). It restores, builds and publishes on Windows, zips the output and creates a GitHub release from a tag such as v2.2-beta, using a notes file from docs/releases/. The inputs control the tag, whether it is a pre-release and which notes file to use. A beta is a pre-release; a build from main with pre-release off becomes the Latest release.

This website is published by a second workflow, pages.yml, which runs site/build.py and deploys the site folder with GitHub Pages. There is no framework or bundler: plain HTML, one CSS file built on design tokens, and one JavaScript file.

Mistakes and lessons

Xbox Y is upside down

DS4 counts Y downward, Xbox upward. Pull Down worked on one pad and pulled up on the other until the Y sign was flipped for Xbox.

"Center" was really Down

The first drift direction called Center was a straight pull down. Renaming it Down and adding Up, Left and Right with the same method removed the confusion. Old profiles that say Center still load as Down.

The wiggle axis

Filtering first shook the same axis as the drift. It now shakes the one across it, so the stick keeps its pull and the wiggle stays centered on neutral.

Never quite at the target

An exponential filter approaches its target forever and never lands on it. A tiny snap threshold (0.001 percent) makes the output exact.

Tests can be wrong too

Several failing checks were bad expectations (a sign, a parity assumption) rather than bad code. Each was worked out before changing anything.

Don't route around blocks

When the package feed refused the sandbox, the fix was to compile without the package and use a stub, not to bypass the proxy.

What is verified, and what is not

Verified

  • The engine maths, timing and gating against a stub controller.
  • Capture state handling, switching and fallback with fakes.
  • The Windows build of the whole app on every push.
  • The numbers shown in the labs on this site.

Needs your eyes on Windows

  • What the real virtual pad shows in joy.cpl.
  • How a particular game reacts to the stick, the rate and the pattern.
  • Raw Input device behaviour with your hardware.
  • Anti-cheat compatibility. The project makes no promise about it.
